## 계획하는 작업 흐름

보안을 책임지게 된 개발자가 다음 질문에 답할 수 있어야 합니다.

1. 이 프로젝트는 무엇을 검사해야 하며, 아직 모르는 것은 무엇인가?
2. 현재 근거로 어떤 행동을 할 수 있고, 이유는 무엇인가?
3. 비교 가능한 다음 실행에서 더 이상 보고되지 않은 것인가, 수용하거나 건너뛴 것인가?
4. 이전 결정 중 지금 다시 검토할 것은 무엇인가?

현재 제품은 의존성 보고서에 대해 2번을 지원합니다. 프로젝트별 설정과 결정 검토
목록은 아직 부족합니다. 실행 비교는 있지만 #247과 #248에서 결정 정보와 출처
보존 결함을 확인했습니다. 아래 순서는 입력 스캐너 확장에 앞서 이 문제를 다룹니다.

## 실행 순서

GitHub의 `roadmap: now`, `roadmap: next`, `roadmap: later`는 순서를 나타냅니다.
진행 상태 라벨·담당자·출시일·계약 변경 승인을 대신하지 않습니다.
진행 상태 라벨은 정확히 하나를 유지합니다. 미배정 작업은 기여자가 맡겠다고
밝힌 뒤 구현하며 기존 담당자는 유지합니다. 설계가 필요한 문제는 패치가 짧아
보여도 첫 기여용 이슈로 취급하지 않습니다.

## 이전 로드맵과 달라진 점

[#125 설계](./specs/adoption-roadmap.ko.md)는 인터페이스 아이디어와 거절한 설계의
기록으로 남깁니다. #140/#136부터 시작하라는 지침은 과거 순서입니다. #136은
배포됐고, 현재 #247/#248이 신뢰성 문제를 보여줬으며 #163이 다음 기능입니다.
현재 순서는 이 문서가, 인터페이스는 개별 명세가 담당합니다. 충돌하는 제안은
코드를 바꾸기 전에 Owner가 명시적으로 결정합니다.

PR #250은 병합되지 않은 제품 설명 제안 #219를 대체합니다. 현재 기능은 PRODUCT에,
실행 순서는 여기에 두며, 보류된 배지 #134를 거절된 작업으로 분류한 오류를
수정합니다. #251은 그 제품 결정을 유지하면서 문구와 공개 경험을 정리합니다.

## 유지와 수용 기준

매 릴리스 때 태그와 병합된 코드로 배포/main/명세/PR 표를 갱신하고 다음 기능의 의존성을
확인합니다. 이슈 정비 시 낡은 상태 라벨을 제거하고 담당자를 유지하며, 전달된
범위나 기록된 거절에 대해서만 닫습니다. 우선순위가 구현 중이라는 뜻은 아닙니다.

전략 문서 병합 전에는 Owner가 대상 사용자·실행 순서·사용성 확인 제안을,
유지관리자가 링크·전달 근거를 검토합니다. 구현 전에는 연결된 이슈·명세와
코드·테스트·보안 리뷰를 따릅니다. 이 문서에 등장했다고 실행 중 사용 정보 수집,
새 실행 동작, baseline 불변 조건, 배포를 승인한 것은 아닙니다.

## 사용성 확인 제안

다음은 앞으로 수행할 평가 제안이며 완료된 사용자 연구가 아닙니다.
동의를 받고 관찰하되, 측정을 위해 제품에 사용 정보 수집이나 네트워크 동작을
추가하지 않습니다.

| 질문 | 수집할 근거 |
|---|---|
| 처음 사용하는 사람이 다음 단계를 찾을 수 있는가? | 유지관리자 5명 중 4명 이상이 도움 없이 5분 안에 지원되는 조치나 부족한 근거를 설명합니다. 실패 사례와 참여자 수를 기록합니다. |
| 조치가 근거에 맞는가? | Fixture와 패키지 실행 검사로 명령, 미지원 대상, 조치 예상 건수의 한계를 확인합니다. |
| 검사 범위를 이해하는가? | 같은 참여자 중 4명 이상이 의존성 판정과 프로젝트 전반의 보안, 도구 설치와 실제 검사를 구분합니다. |
| 결정이 보존되는가? | 회귀 검사로 식별 정보, 작성자, 사유, 만료일 보존과 누락 소스 표시를 확인합니다. |
| 다시 사용할 때 도움이 되는가? | 만료·변경 항목의 시범 보고서에서 유지관리자가 각 항목의 근거를 추적하고 설명할 수 있는지 관찰합니다. |

측정 전에는 재사용률이나 조치 시간 개선을 주장하지 않습니다.
발견 건수, 별 개수, baseline 수용만으로 성공을 판단하지 않습니다.
