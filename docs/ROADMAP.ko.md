## 도달하려는 곳

보안을 책임지게 된 개발자가 다음 네 질문에 답할 수 있어야 합니다.

1. 이 프로젝트는 무엇을 검사해야 하며, 아직 모르는 것은 무엇인가?
2. 현재 근거로 어떤 행동을 할 수 있고, 이유는 무엇인가?
3. 비교 가능한 다음 실행에서 더 이상 보고되지 않은 것인가, 수용하거나 건너뛴 것인가?
4. 이전 결정 중 지금 다시 검토할 것은 무엇인가?

현재 가장 강한 부분은 지원하는 의존성 리포트에 대한 2번입니다. 1번과 4번은
큰 공백입니다. 3번은 있지만 결정 정보와 출처 보존에 결함이 있습니다.
이 공백을 두고 scanner 수만 늘리면 입력은 넓어져도 사용자의 일이 완성되지 않습니다.

## 실행 순서

GitHub의 `roadmap: now`, `roadmap: next`, `roadmap: later`는 순서를 나타냅니다.
수명주기 라벨·담당자·출시일·계약 변경 승인을 대신하지 않습니다.
수명주기 라벨은 정확히 하나를 유지합니다. 미배정 작업은 기여자가 맡겠다고
밝힌 뒤 구현하며 기존 담당자는 유지합니다. 설계가 필요한 문제는 패치가 짧아
보여도 첫 기여용 이슈로 취급하지 않습니다.

## 이전 로드맵과 달라진 점

[#125 설계](./specs/125-adoption-roadmap.md)는 인터페이스 아이디어와 거절한 설계의
기록으로 남깁니다. #140/#136부터 시작하라는 지침은 과거 순서입니다. #136은
배포됐고, 현재 #247/#248이 신뢰성 공백을 드러냈으며 #163이 다음 기능입니다.
현재 순서는 이 문서가, 인터페이스는 개별 명세가 담당합니다. 충돌하는 제안은
코드를 바꾸기 전에 Owner가 명시적으로 결정합니다.

미머지 포지셔닝 PR #219는 채택하지 않았습니다. #134를 거절한 작업으로 잘못
묶었고 별도의 horizon 문서를 유지했습니다. #249의 대체 PR은 약속을 PRODUCT에,
구현 근거를 여기에 모읍니다. 두 서술을 함께 머지하기보다 전체 대체안을 검토합니다.

## 유지와 수용 기준

매 릴리즈 때 tag·머지 코드로 배포/main/명세/PR 표를 갱신하고 다음 기능의 의존성을
확인합니다. 이슈 정비 시 낡은 상태 라벨을 제거하고 담당자를 유지하며, 전달된
범위나 기록된 거절에 대해서만 닫습니다. 우선순위가 구현 중이라는 뜻은 아닙니다.

전략 문서 머지 전에는 Owner가 캐치프레이즈·사용자·순서·시범 사용 기준을,
maintainer가 링크·전달 근거를 검토합니다. 구현 전에는 연결된 이슈·명세와
코드·테스트·보안 리뷰를 따릅니다. 이 문서에 등장했다고 runtime telemetry,
새 실행 동작, baseline 불변 조건, 배포를 승인한 것은 아닙니다.
