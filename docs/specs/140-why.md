# Feature specification: explain a vulnerable dependency path

## Issue and lifecycle metadata

- Issue: [#140](https://github.com/zero-shelter/zero-shelter/issues/140)
- Target layer: lockfile, CLI, report
- Related PR: pending

## Problem

A scanner can name a vulnerable transitive package and a fixed version without showing which direct dependency brought it into the project. Maintainers still have to inspect the lockfile before deciding what to upgrade.

## Goal

`zero-shelter why <package>` prints every dependency path from a root dependency to each installed copy of the named package. When a supplied scanner finding names a fixed version, it also reports the lowest direct package version already present in the lockfile whose dependency path accepts that fixed version. If the lockfile cannot establish that answer, the output says so and names the blocking range.

## Scope

### Included

- `why <package>` on npm `package-lock.json` v2/v3 package maps.
- Repeatable `--input` scanner reports, so the command is deterministic in CI and does not require live scanners.
- Text (default) and `--format json` output.
- All simple paths with cycle protection, duplicate package versions, workspaces as path nodes, and direct dependency roots.
- No registry lookup and no package installation.

### Explicitly excluded

- Yarn and pnpm lockfile parsing; tracked separately by #156.
- Applying upgrades or writing project files.
- Claiming a version exists when it is not present in the lockfile.
- Reachability or exploitability conclusions.

## Interface

| Direction | Contract |
|---|---|
| Input | `zero-shelter why <package> [--cwd <dir>] [--input <report>]... [--format json]` |
| Output | Text names installed versions and paths. JSON has `package`, `versions`, `paths`, `findings`, and `blockers`. |
| Errors/exit code | Missing package or unreadable lockfile exits 2 with the path/package named. No matching finding is a valid path-only result. |
| Compatibility | Existing `judge`, `history`, hook, SARIF, and report outputs remain unchanged. |

## Architecture

- Layer(s) changed: `src/lockfile.ts`, new `src/why.ts`, `src/cli.ts`.
- Files expected to change: the three modules above, `test/why.test.ts`, `test/lockfile-facts.test.ts`, and this spec/translation.
- Shared contracts touched: `InstalledVersions` gains optional graph metadata; existing fields and output schemas remain unchanged.
- Possible conflicts: future pnpm support (#156) must reuse the graph interface without changing `why` output semantics.

## Security and privacy

- Protected or sensitive data: local package names, versions, and lockfile paths already read by the judge.
- Data flow and trust boundary: read local lockfile and optional local scanner files; render locally.
- Logging and retention: stdout only unless the caller redirects it; no files are written.
- Network/LLM/telemetry behavior: no new network behavior; without `--input`, the command reuses the existing scanner subprocesses and their documented network behavior.
- Failure mode: fail-closed for unreadable/missing input; path-only output when no finding data is available.
- User opt-in/opt-out: command is explicit; existing commands are unchanged.

## QA acceptance criteria

| Scenario | Expected result | Evidence |
|---|---|---|
| Normal input | A transitive package prints at least one root-to-copy path and fixed-version context when supplied | `test/why.test.ts` |
| Invalid input | Unknown package and malformed/missing lockfile exit 2 with a useful message | CLI tests |
| Empty input | A package with no matching scanner finding still prints paths and no invented fix | unit/CLI tests |
| Boundary/large input | Duplicate copies and a cycle terminate deterministically without duplicate paths | table-driven unit tests |
| Existing behavior | Existing suite and contract snapshots pass unchanged | `npm test` |
| Security/privacy abuse case | No network module or write is introduced | `test/promises.test.ts` |

## Agent notes

Keep the path walk deterministic: sort roots, edges, versions, and rendered findings. A lockfile records installed edges and requested ranges; it cannot prove a registry version exists. Never turn an absent answer into an upgrade command.

## Decision log

| Decision | Alternatives considered | Reason |
|---|---|---|
| Use explicit `--input` reports instead of always spawning scanners | Reimplement the whole judge collection flow inside `why` | Repeatable, offline, and avoids changing scanner execution behavior in the first PR |
| Add optional graph metadata to `InstalledVersions` | Reconstruct paths from package names at render time | Resolution belongs beside lockfile parsing and must be reusable by pnpm later |
| Report only versions already present in the lockfile | Query npm for the lowest available release | Preserves the no-network invariant and avoids a false promise |
